# Fields API

REST API для управління сільськогосподарськими полями. Головна задача — за координатами точки знайти всі поля, які її містять, на базі з десятків тисяч полігонів.

## Запуск

```bash
make start
```

Піднімає PostgreSQL 16 + PostGIS 3.4, накочує міграції та засіває 50 000 полів. Swagger: http://localhost:8000/docs

Інші команди:

| Команда | Дія |
|---|---|
| `make test` | 23 тести (юніт + інтеграційні) |
| `make bench` | заміри швидкості пошуку з індексом і без |
| `make explain` | план виконання головного запиту |
| `make index-off` / `make index-on` | зняти / повернути GiST-індекс |
| `make seed COUNT=1000` | перегенерувати дані |
| `make psql`, `make logs`, `make clean` | консоль БД, логи, видалити все |

Без `make`: `docker compose up -d --build`, далі `docker compose exec api alembic upgrade head` і `docker compose exec api python -m scripts.seed --truncate`.

### Конфігурація

Дефолти зашиті в `docker-compose.yml`, тож проєкт стартує без підготовки. Для перевизначення — скопіюйте `.env.example` у `.env`: `POSTGRES_USER`/`POSTGRES_PASSWORD` (`postgres`), `POSTGRES_DB` (`fields`), `POSTGRES_PORT`, `API_PORT`.

`DATABASE_URL` навмисно не має значення за замовчуванням у коді: креденшели не повинні лежати в репозиторії, а мовчазний фолбек на випадкову базу гірший за падіння на старті.

## API

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/api/fields` | Створити поле |
| `GET` | `/api/fields` | Список із фільтрами `crop`, `owner`, `min_area`, `max_area`, `limit`, `offset` |
| `GET` | `/api/fields/find-by-point` | **Поля, що містять точку** (`lon`, `lat`) |
| `GET` | `/api/fields/{id}` | Деталі з повною геометрією |
| `GET` | `/health` | Стан сервісу та з'єднання з БД |

```bash
curl -X POST localhost:8000/api/fields -H 'Content-Type: application/json' -d '{
  "name": "Поле №1 - Пшениця",
  "geometry": {"type": "Polygon", "coordinates": [[
    [30.5234, 50.4501], [30.5334, 50.4501], [30.5334, 50.4601],
    [30.5234, 50.4601], [30.5234, 50.4501]]]},
  "crop": "Пшениця", "owner": "Іванов І.І."}'

curl 'localhost:8000/api/fields/find-by-point?lon=30.5250&lat=50.4550'
```

Відповідь пошуку містить `query_point`, список полів із `distance_to_center_m` та `query_time_ms`. Точка може потрапити в кілька полів — повертаються всі, відсортовані за відстанню до центроїда.

Геометрія в списку не повертається, лише метадані: полігон на 12 вершин × 100 записів — це десятки зайвих кілобайт на запит.

### Валідація і помилки

Формат: `{"detail": "...", "code": "..."}`.

| Ситуація | HTTP | `code` |
|---|---|---|
| Структура запиту (тип, замкненість кільця, діапазони координат) | 422 | `validation_error` |
| Самоперетин полігона | 422 | `invalid_geometry` |
| Дірки в полігоні | 422 | `unsupported_geometry` |
| Площа ≤ 0.1 га | 422 | `area_too_small` |
| Поле не знайдено | 404 | `not_found` |

Структуру перевіряє Pydantic, геометрію та площу — PostGIS одним запитом перед вставкою. Валідація саме в базі, а не в Shapely, щоб не було розбіжності між тим, що дозволяє застосунок, і тим, що дозволяє `CHECK`-констрейнт.

## Архітектура

```
app/
├── main.py           FastAPI, обробники помилок, /health
├── db.py             engine, сесія (одна транзакція на запит)
├── models.py         SQLAlchemy-модель — джерело метаданих для Alembic
├── geometry.py       чисті обчислення без БД (покриті юніт-тестами)
├── schemas.py        Pydantic-моделі запитів і відповідей
├── repository.py     увесь SQL
├── service.py        бізнес-правила
├── middleware.py     ASGI-логування запитів
└── routers/fields.py HTTP-маршрути
```

`router → service → repository`: router знає про HTTP і не знає про SQL, service знає про бізнес-правила й кидає доменні винятки, repository знає лише про SQL. Коміт транзакції робить залежність `get_session`, а не репозиторій — інакше репозиторій керував би межами транзакції.

Логування запитів — чиста ASGI-мідлвара, а не `@app.middleware("http")`: останній базується на `BaseHTTPMiddleware`, який на кожен запит створює anyio-стрім і таск-групу. У завданні про продуктивність вимірювач не повинен сам додавати оверхед.

## Схема БД

```sql
CREATE TABLE fields (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        TEXT NOT NULL,
    geom        geometry(Polygon, 4326) NOT NULL,
    area_ha     DOUBLE PRECISION NOT NULL,
    crop        TEXT NOT NULL,
    owner       TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fields_geom_valid    CHECK (ST_IsValid(geom)),
    CONSTRAINT fields_area_positive CHECK (area_ha > 0.1)
);

CREATE INDEX fields_geom_gist ON fields USING GIST (geom);   -- міграція 0002
CREATE INDEX fields_crop_idx  ON fields (crop);
CREATE INDEX fields_owner_idx ON fields (owner);
CREATE INDEX fields_area_idx  ON fields (area_ha);
```

**Типізована колонка замість GeoJSON у `jsonb`** — бінарне зберігання, кешований bounding box і можливість просторового індексу. У `jsonb` індексувати просторове відношення неможливо.

**SRID 4326** — дані приходять у градусах від GPS, а предикат «точка в полігоні» від проєкції не залежить. Метрика рахується окремо кастом у `geography`.

**GiST, а не B-tree** — B-tree впорядковує одновимірні значення, для прямокутників «більше/менше» не визначене. GiST будує R-tree: кожен вузол охоплює прямокутники нащадків, пошук спускається лише у відповідні гілки.

**Не SP-GiST і не BRIN** — SP-GiST виграє на рівномірних точках, а не на полігонах різного розміру; BRIN дає виграш лише коли рядки фізично впорядковані за розташуванням, чого при довільній вставці немає.

**Денормалізована `area_ha`** — фільтр по обчислюваному `ST_Area(...)` не використав би індекс. Площа рахується один раз при вставці.

**Площа через `ST_Area(geom::geography)/10000`** — у квадратних градусах площа безглузда: на широті Києва градус довготи ≈ 71 км, широти ≈ 111 км.

**Без унікальності по `name`** — однакові назви полів у різних господарств нормальні; природним ключем був би `(owner, name)`.

## Як працює пошук за точкою

```sql
SELECT id, name, area_ha, crop, owner,
       ST_Distance(ST_Centroid(geom)::geography,
                   ST_SetSRID(ST_MakePoint(:lon, :lat), 4326)::geography) AS distance_to_center_m
FROM fields
WHERE ST_Contains(geom, ST_SetSRID(ST_MakePoint(:lon, :lat), 4326))
ORDER BY distance_to_center_m;
```

`ST_Contains` — не одна операція, а дві, і це видно в плані:

```
->  Index Scan using fields_geom_gist on fields
      Index Cond: (geom ~ '...'::geometry)
      Filter: st_contains(geom, '...'::geometry)
```

- **Index Cond** — груба фаза: оператор `~` порівнює лише bounding box-и («прямокутник поля містить точку»). Завдяки R-tree перевіряються не всі 50 000 полів, а близько `log(n)` вузлів.
- **Filter** — точна фаза: справжня перевірка належності запускається лише для кандидатів, що пройшли першу.

Без індексу лишається друга фаза для кожного рядка: `Parallel Seq Scan ... Rows Removed by Filter: 24999`.

## Продуктивність

`scripts/benchmark.py`: 300 точок на прогін, 70% із центрів наявних полів, 30% випадкові по Україні. Той самий запит виконується з індексом і з примусовим `seq scan`.

| Полів у БД | З GiST-індексом (p50) | Без індексу (p50) | Прискорення |
|---|---|---|---|
| 1 000 | 0.16 мс | 0.36 мс | ×2 |
| 10 000 | 0.12 мс | 5.42 мс | ×45 |
| 50 000 | 0.25 мс | 181.58 мс | ×739 |

Важлива не остання цифра, а форма залежності: **час із індексом не змінюється при зростанні таблиці в 50 разів** (глибина дерева росте логарифмічно), без індексу росте лінійно й гірше. Звідси ж чесний висновок: на 1 000 рядків індекс майже не потрібен — саме тому seed за замовчуванням генерує 50 000.

Два нюанси вимірювань:

- **Перший запит після старту — 15–20 мс**, а не частка мілісекунди: підняття з'єднання, планування, прогрів кешу. Тому рахується медіана по сотнях запитів.
- **asyncpg кешує підготовлені запити**, тому після `SET enable_indexscan = off` виконувався б план, побудований ще з індексом — бенчмарк показував «без індексу швидше». Лікується окремим з'єднанням зі `statement_cache_size=0` та `DISCARD PLANS`.

## Seed

Поля генеруються навколо центрів дванадцяти областей, а не рівномірним шумом — реальні поля групуються.

Кожне поле — 6–12 вершин радіусом 120–1500 м. Вершини ставляться по одній у рівні сектори кола з випадковим зсувом у межах сектора. Це конструктивно гарантує монотонність кута (немає самоперетинів) і відсутність злиплих вершин після округлення координат — тобто `ST_IsValid` проходить без перевірок постфактум.

Близько 12% полів зсуваються від попереднього на відстань, меншу за 60% власного радіуса — при джитері радіуса 30% це гарантує перетин. Перевірено на згенерованих даних: 5 994 таких пари, перетинаються всі 5 994.

Після вставки виконується `ANALYZE fields`: без свіжої статистики планувальник може проігнорувати індекс.

## Тести

23 тести. **Юніт** — чисті функції з `geometry.py`: замкненість кільця, межі координат, конвертація метрів у градуси, інваріанти генератора полігонів. **Інтеграційні** — проти реального PostGIS: створення з обчисленням площі, відмови на самоперетині, незамкненому кільці, дірці й замалій площі, пошук у точці перетину двох полів, фільтри, пагінація, 404.

Геометрію мокати немає сенсу — саме вона є предметом тестування. Тести працюють з окремою базою `fields_test`, схема якої накочується тією самою міграцією. Ізоляція — транзакція з відкатом після кожного тесту.

## Обмеження та що далі

- Підтримується лише простий полігон з одним кільцем: дірки та MultiPolygon відхиляються. Розширення — колонка `geometry(MultiPolygon, 4326)` з `ST_Multi()` на вставці.
- `ST_Contains` не включає межу: точка рівно на спільному ребрі двох полів не належить жодному. Якщо така семантика небажана — `ST_Intersects` (план виконання і використання індексу ідентичні).
- Пагінація через `OFFSET` деградує на великих зміщеннях; `total` рахує всі відфільтровані рядки (~40 мс на 50 000). Наступний крок — keyset-пагінація.
- Немає `UPDATE`/`DELETE`. Якби вони з'явились, `area_ha` треба було б перераховувати — або зробити колонку `GENERATED ALWAYS AS (...) STORED`.
- Немає аутентифікації, rate limiting і CORS — браузерного клієнта в завданні немає.
- Складені індекси має сенс додавати після аналізу `pg_stat_statements`, а не навмання; на мільйонах рядків — партиціонування за регіоном і `CLUSTER` за геометрією, що відкриває дорогу дешевому BRIN.
