# Fields API

REST API для управління сільськогосподарськими полями з швидким пошуком полів за координатами точки.

Основна задача — за парою `(lon, lat)` знайти всі поля, які містять цю точку, на базі з десятків тисяч полігонів. Усе інше в проєкті підпорядковане цій задачі.

## Швидкий старт

```bash
docker compose up -d --build
```

Команда піднімає PostgreSQL 16 з PostGIS 3.4, накочує міграції та запускає API на `http://localhost:8000`.

Заповнити базу тестовими даними:

```bash
docker compose exec api python -m scripts.seed --count 50000 --truncate
```

Перевірити, що все живе:

```bash
curl localhost:8000/health
```

Swagger UI: http://localhost:8000/docs

### Конфігурація

Усе налаштовується змінними оточення, значення за замовчуванням зашиті в `docker-compose.yml`, тому проєкт піднімається без жодної підготовки. Щоб щось перевизначити — скопіюйте `.env.example` у `.env`:

| Змінна | За замовчуванням | Призначення |
|---|---|---|
| `POSTGRES_USER` | `postgres` | Користувач БД |
| `POSTGRES_PASSWORD` | `postgres` | Пароль БД |
| `POSTGRES_DB` | `fields` | Назва бази |
| `POSTGRES_PORT` | `5432` | Порт БД на хості |
| `API_PORT` | `8000` | Порт API на хості |
| `DATABASE_URL` | складається з `POSTGRES_*` | Потрібна явно лише при запуску поза Docker |

`DATABASE_URL` навмисно не має значення за замовчуванням у коді: креденшели не повинні лежати в репозиторії, а мовчазний фолбек на випадкову базу гірший за падіння на старті з зрозумілою помилкою.

Пароль `postgres` у дефолтах — свідомо: це локальне dev-оточення, яке має підніматися однією командою. У проді ці значення прийшли б із секрет-менеджера, а порт БД взагалі не публікувався б на хост.

## API

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/api/fields` | Створити поле |
| `GET` | `/api/fields` | Список полів із фільтрами та пагінацією |
| `GET` | `/api/fields/find-by-point` | **Знайти поля, що містять точку** |
| `GET` | `/api/fields/{id}` | Деталі поля з повною геометрією |
| `GET` | `/health` | Стан сервісу та з'єднання з БД |

### POST /api/fields

```bash
curl -X POST localhost:8000/api/fields \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Поле №1 - Пшениця",
    "geometry": {
      "type": "Polygon",
      "coordinates": [[
        [30.5234, 50.4501], [30.5334, 50.4501],
        [30.5334, 50.4601], [30.5234, 50.4601],
        [30.5234, 50.4501]
      ]]
    },
    "crop": "Пшениця",
    "owner": "Іванов І.І."
  }'
```

Відповідь `201 Created`:

```json
{
  "id": "347e88f1-e3fc-4434-bff1-32cb0105b084",
  "name": "Поле №1 - Пшениця",
  "geometry": { "type": "Polygon", "coordinates": [[...]]},
  "area_ha": 78.99741385955811,
  "crop": "Пшениця",
  "owner": "Іванов І.І.",
  "created_at": "2026-09-23T18:32:09.686904Z"
}
```

Валідація відбувається у два етапи:

1. **Структура** (Pydantic): тип `Polygon`, кільце замкнене (перша точка дорівнює останній), щонайменше 4 точки, координати в межах `lon ∈ [-180, 180]`, `lat ∈ [-90, 90]`.
2. **Геометрія та бізнес-правила** (PostGIS): полігон без самоперетинів (`ST_IsValid`), площа більша за 0.1 га.

### GET /api/fields

Параметри: `crop`, `owner`, `min_area`, `max_area`, `limit` (за замовчуванням 20, максимум 100), `offset`.

```bash
curl 'localhost:8000/api/fields?crop=Пшениця&min_area=50&limit=5'
```

```json
{
  "total": 150,
  "fields": [
    {"id": "...", "name": "Поле №1", "area_ha": 45.2, "crop": "Пшениця", "owner": "Іванов І.І."}
  ]
}
```

Геометрія в списку не повертається — тільки метадані. Полігон на 12 вершин помножити на 100 записів дає десятки кілобайт зайвого JSON на кожен запит.

### GET /api/fields/find-by-point

```bash
curl 'localhost:8000/api/fields/find-by-point?lon=30.5250&lat=50.4550'
```

```json
{
  "query_point": {"lon": 30.525, "lat": 50.455},
  "fields": [
    {
      "id": "...",
      "name": "Поле №1 - Пшениця",
      "area_ha": 78.99,
      "crop": "Пшениця",
      "owner": "Іванов І.І.",
      "distance_to_center_m": 241.71
    }
  ],
  "query_time_ms": 0.34
}
```

Точка може потрапити в кілька полів, якщо вони перекриваються — повертаються всі, відсортовані за відстанню до центроїда.

### Помилки

Єдиний формат: `{"detail": "...", "code": "..."}`.

| Ситуація | HTTP | `code` |
|---|---|---|
| Порушення структури запиту | 422 | `validation_error` |
| Полігон із самоперетинами | 422 | `invalid_geometry` |
| Дірки в полігоні (кілька кілець) | 422 | `unsupported_geometry` |
| Площа ≤ 0.1 га | 422 | `area_too_small` |
| Поле не знайдено | 404 | `not_found` |
| БД недоступна (`/health`) | 503 | `database_unavailable` |

## Архітектура

```
app/
├── main.py           FastAPI, обробники помилок, /health
├── config.py         налаштування з env
├── db.py             async engine, фабрика сесій
├── models.py         SQLAlchemy 2.0 модель Field
├── geometry.py       чисті геометричні обчислення без БД
├── schemas.py        Pydantic-моделі запитів і відповідей
├── repository.py     увесь SQL
├── service.py        бізнес-правила
├── middleware.py     ASGI-мідлвара логування
└── routers/fields.py HTTP-маршрути
```

Три шари з односторонньою залежністю `router → service → repository`:

- **router** знає про HTTP (коди статусів, query-параметри) і не знає про SQL;
- **service** знає про бізнес-правила (полігон має бути валідним, площа > 0.1 га) і не знає про HTTP — він кидає доменні винятки, які застосунок перетворює на HTTP-коди;
- **repository** знає про SQL і не знає про бізнес-правила.

Окремо винесено `geometry.py` — чисті функції, які не потребують БД (замкненість кільця, межі координат, конвертація метрів у градуси, побудова кільця для seed). Вони покриті юніт-тестами. Усе, що вимагає PostGIS, живе в SQL і покрите інтеграційними тестами.

## Схема БД

```sql
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE fields (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        TEXT NOT NULL,
    geom        geometry(Polygon, 4326) NOT NULL,
    area_ha     DOUBLE PRECISION NOT NULL,
    crop        TEXT NOT NULL,
    owner       TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fields_geom_valid    CHECK (ST_IsValid(geom)),
    CONSTRAINT fields_area_positive CHECK (area_ha > 0.1)
);

CREATE INDEX fields_geom_gist ON fields USING GIST (geom);
CREATE INDEX fields_crop_idx  ON fields (crop);
CREATE INDEX fields_owner_idx ON fields (owner);
CREATE INDEX fields_area_idx  ON fields (area_ha);
```

### Чому саме так

**Типізована колонка `geometry(Polygon, 4326)`, а не GeoJSON у `jsonb`.** Типізована колонка зберігає геометрію в бінарному вигляді, тримає кешований bounding box і дозволяє побудувати просторовий індекс. У `jsonb` індексувати просторове відношення неможливо — довелося б витягувати всі рядки в Python.

**SRID 4326 (WGS84).** Вхідні дані приходять у градусах довготи й широти, як їх віддає GPS. Топологічний предикат «точка всередині полігона» від проєкції не залежить, тому конвертувати геометрію не потрібно. Метричні величини рахуються окремо — див. нижче.

**GiST, а не B-tree.** B-tree впорядковує одновимірні значення; для двовимірних прямокутників відношення «більше/менше» не визначене. GiST — узагальнене збалансоване дерево, у якому для геометрії будується R-tree: кожен вузол зберігає прямокутник, що охоплює прямокутники нащадків. Пошук спускається лише в ті гілки, чий прямокутник накриває точку.

**GiST, а не SP-GiST або BRIN.** SP-GiST (quadtree) виграє на рівномірних наборах точок; для полігонів дуже різного розміру GiST поводиться передбачуваніше. BRIN дає виграш лише коли рядки фізично впорядковані за розташуванням — при довільному порядку вставки його зони стають надто широкими і майже нічого не відсікають.

**Денормалізована колонка `area_ha`.** Фільтр за площею по обчислюваному на льоту `ST_Area(...)` не зміг би використати індекс — знадобився б functional index із точно таким самим виразом у `WHERE`. Площа рахується один раз при вставці і індексується звичайним B-tree.

**Площа через `ST_Area(geom::geography) / 10000`.** Площа в квадратних градусах фізичного змісту не має: на широті Києва градус довготи ≈ 71 км, а градус широти ≈ 111 км. Каст у `geography` змушує PostGIS рахувати на еліпсоїді WGS84 і повертати м².

**`CHECK (ST_IsValid(geom))`.** Інваріант «у таблиці немає невалідних полігонів» тримається базою, а не лише застосунком. Захищає й від даних, залитих повз API — наприклад, seed-скриптом.

**Немає унікальності по `name`.** Однакові назви полів у різних господарств — звичайна річ. Природним ключем був би `(owner, name)`, але ТЗ цього не вимагає.

## Як працює пошук за точкою

```sql
SELECT id, name, area_ha, crop, owner,
       ST_Distance(ST_Centroid(geom)::geography,
                   ST_SetSRID(ST_MakePoint(:lon, :lat), 4326)::geography) AS distance_to_center_m
FROM fields
WHERE ST_Contains(geom, ST_SetSRID(ST_MakePoint(:lon, :lat), 4326))
ORDER BY distance_to_center_m;
```

`ST_Contains` — не одна операція, а дві. Планувальник розкриває його у двофазний пошук, і це видно в плані виконання:

```
->  Index Scan using fields_geom_gist on fields
      Index Cond: (geom ~ '...'::geometry)
      Filter: st_contains(geom, '...'::geometry)
```

- **Index Cond** — груба фаза (*filter*). Оператор `~` порівнює лише bounding box-и: «чи накриває прямокутник поля прямокутник точки». Це чотири порівняння чисел, а завдяки R-tree всередині GiST перевіряти доводиться не всі 50 000 полів, а близько `log(n)` вузлів дерева.
- **Filter** — точна фаза (*refine*). Справжня перевірка належності (ray casting) виконується лише для кількох кандидатів, що пройшли першу фазу.

Без індексу лишається тільки друга фаза, і вона запускається для кожного рядка таблиці:

```
->  Parallel Seq Scan on fields
      Filter: st_contains(geom, '...'::geometry)
      Rows Removed by Filter: 24999
```

## Продуктивність

Заміряно скриптом `scripts/benchmark.py`: 300 точок на прогін, 70% із них узяті з центрів наявних полів (гарантовано влучають), 30% випадкові по території України. Той самий запит виконується двічі — з доступним індексом і з примусово вимкненим (`SET enable_indexscan = off`, `SET enable_bitmapscan = off`).

| Полів у БД | З GiST-індексом (p50) | Без індексу (p50) | Прискорення |
|---|---|---|---|
| 1 000 | 0.16 мс | 0.36 мс | ×2 |
| 10 000 | 0.12 мс | 5.42 мс | ×45 |
| 50 000 | 0.25 мс | 181.58 мс | ×739 |

Головне в цій таблиці — не остання цифра, а форма залежності. **Час пошуку з індексом практично не змінюється при зростанні таблиці в 50 разів**, бо глибина дерева росте логарифмічно. Час без індексу росте лінійно (а після 10 000 ще й гірше за лінійний — вмикається JIT-компіляція виразів і паралельні воркери, які самі мають вартість).

Звідси ж чесне застереження: **на 1 000 рядків індекс майже не потрібен** — таблиця займає кілька сторінок і сканується швидше, ніж обходиться дерево. Саме тому seed за замовчуванням генерує 50 000 полів: на мінімальній тисячі з ТЗ різницю просто не видно.

Ще одна деталь, помітна неозброєним оком: **перший запит після старту контейнера займає 15–20 мс**, а не частку мілісекунди. Це не робота індексу — це підняття з'єднання в пулі, планування запиту та прогрів кешу сторінок. Уже другий однаковий запит виконується за десяті частки мілісекунди. Тому бенчмарк рахує медіану по сотнях запитів, а не час одного.

Відтворити:

```bash
docker compose exec api python -m scripts.seed --count 50000 --truncate
docker compose exec api python -m scripts.benchmark --points 1000
```

Нюанс, на який варто зважати при вимірюваннях: asyncpg кешує підготовлені запити, і після `SET enable_indexscan = off` продовжував би виконуватись план, побудований ще з індексом. Тому бенчмарк використовує окреме з'єднання з вимкненим кешем (`statement_cache_size=0`) і додатково робить `DISCARD PLANS`. Без цього вимірювання показувало б, що «без індексу швидше», що фізично неможливо.

## Seed

```bash
docker compose exec api python -m scripts.seed --count 50000 --truncate
```

Генерує поля навколо центрів дванадцяти областей України, а не рівномірним шумом по прямокутнику — реальні поля групуються, і це також робить навантаження на індекс реалістичнішим.

Кожне поле — багатокутник із 6–12 вершин радіусом 120–1500 м. Вершини ставляться по одній у рівні сектори кола з випадковим зсувом у межах сектора. Це дає дві гарантії без жодної перевірки постфактум: кут монотонно зростає (межа не перетинає сама себе) і вершини не злипаються після округлення координат. Обидві потрібні, щоб полігон пройшов `ST_IsValid`.

Близько 12% полів генеруються як зсув попереднього на відстань, меншу за радіус — вони гарантовано перекриваються, що дає матеріал для перевірки multiple matches. На 50 000 полів знаходяться поля з десятком перекриттів.

Після вставки скрипт виконує `ANALYZE fields`: без свіжої статистики планувальник може проігнорувати індекс.

## Тести

```bash
docker compose exec api python -m pytest tests -q
```

23 тести, дві групи:

- **юніт** (`tests/unit/`) — чисті функції з `app/geometry.py`: замкненість кільця, межі координат, конвертація метрів у градуси, інваріанти генератора полігонів (кут зростає по колу, вершини не дублюються);
- **інтеграційні** (`tests/integration/`) — проти реального PostGIS: створення поля з обчисленням площі, відмови на самоперетині, незамкненому кільці, дірці та замалій площі, пошук у точці перетину двох полів, фільтри, пагінація, 404.

Геометричну логіку немає сенсу мокати — саме вона є предметом тестування. Інтеграційні тести працюють з окремою базою `fields_test`, схема якої накочується тією самою міграцією Alembic, що й у проді. Ізоляція — транзакція з відкатом після кожного тесту.

## Прийняті рішення та альтернативи

| Рішення | Альтернатива | Чому обрано саме це |
|---|---|---|
| `geometry` + `::geography` для метрики | Колонка типу `geography` | Метрика потрібна лише для площі й відстані; тримати всю геометрію на еліпсоїді означало б платити за сфероїдну математику в кожній перевірці належності |
| PostGIS | `jsonb` + bbox-колонки + Shapely | Формально ТЗ вимагає лише PostgreSQL 14+, але тоді груба фаза стає B-tree по чотирьох колонках, а точна перевірка тягне дані в Python |
| `ST_Area(::geography)` | `ST_Transform` в UTM 36N | UTM швидший, але Україна лежить у двох зонах (35N і 36N) — для заходу країни результат був би зміщений |
| `COUNT(*) OVER ()` | Окремий `SELECT COUNT(*)` | Один похід до БД замість двох і гарантована узгодженість `total` зі сторінкою |
| Чиста ASGI-мідлвара | `@app.middleware("http")` | Останній базується на `BaseHTTPMiddleware`, який на кожен запит створює anyio-стрім і таск-групу. Вимірювач не повинен сам додавати оверхед |
| Валідація геометрії в PostGIS | Shapely в Python | Єдине джерело істини: інакше можлива ситуація, коли Python вважає полігон валідним, а `CHECK` у базі — ні, і користувач отримує 500 замість зрозумілої 422 |
| Батчовий `INSERT` у seed | `COPY` | `COPY` швидший на порядок, але вимагає готувати геометрію в WKB на боці клієнта; 50 000 рядків вставляються за 6 секунд і так |

## Обмеження поточної версії

- Підтримується лише простий полігон з одним кільцем. Дірки (ставок посеред поля) і MultiPolygon (поле з двох роз'єднаних шматків) відхиляються з кодом `unsupported_geometry`.
- Немає `UPDATE`/`DELETE` — у ТЗ вони не вимагаються. Якби з'явився `UPDATE` геометрії, `area_ha` треба було б перераховувати; альтернатива — зробити колонку `GENERATED ALWAYS AS (...) STORED`.
- Пагінація через `OFFSET` деградує на великих зміщеннях.
- Немає аутентифікації, rate limiting і CORS — браузерного клієнта в завданні немає.

## Що б я покращив, маючи більше часу

- **Keyset-пагінація** замість `OFFSET`: `WHERE (created_at, id) < (:last_created_at, :last_id)`. `OFFSET 100000` змушує базу прочитати й відкинути сто тисяч рядків.
- **Складені індекси під реальні патерни фільтрації** — після аналізу `pg_stat_statements`, а не навмання. Зараз окремі B-tree індекси, і планувальник комбінує їх bitmap-скануванням.
- **Партиціонування за регіоном** і `CLUSTER` таблиці за геометрією — від мільйонів рядків це дає і менші індекси, і можливість використати дешевий BRIN.
- **Підтримка MultiPolygon і дірок** — `geometry(MultiPolygon, 4326)` з `ST_Multi()` на вставці уніфікувала б зберігання.
- **Кешування** на рівні reverse proxy для частих однакових точок і **rate limiting**.
- **Навантажувальне тестування** (k6) з профілем «багато пошуків, мало записів», щоб побачити поведінку під конкурентністю, а не лише латентність одного запиту.
- **`ST_Simplify`** для віддачі геометрії на карту в дрібному масштабі — клієнту рідко потрібні всі вершини.
